# ADR-010: paper に信用取引を public のみの近似シミュレーションとして足す

## ステータス

Accepted（2026-11-24）

起票は 2026-11-23（Proposed）。計画書 [`docs/dev/paper-margin-plan.md`](../dev/paper-margin-plan.md) の Step 0 の仕様確認は、
2026-11-24 に #PM-0〜#PM-3 が確定した（最新の `/spot/pairs`、bitbank の信用取引ルールと契約締結前交付書面の原文、
このリポの税務調査の実測）。#PM-4（評価価格）だけが公表資料に無く、決定 3 の仮定として申告する。
#PM-5（実口座との算式突合）は公表ルールの検算で、Accepted の条件にはしない。

## コンテキスト

`paper` は「ライブ価格 × 仮想資金」の練習用サブコマンドで、CLAUDE.md の例外節により
ローカル状態（`~/.bitbank/paper-state.json`）を持つ。叩くのは **public の ticker・candlestick・pairs だけ**で、
private / trade には触れない（chaos `x09` が import を検査する）。現状は現物だけで、
売り越しは `computePositions` が拒否する。

信用の発注（実口座）は [ADR-009](009-margin-order-separate-command.md) で
`trade create-margin-order` として分離することが決まっている（Phase 7、実装は未着手）。
ADR-009 は「`paper` での信用シミュレーション」をスコープ外にしていた。証拠金・金利・
ロスカットのモデルが要り、paper の前提を超えるからである。本 ADR はそれを取り上げる。

信用の paper には、現物に無い要素が要る:

- 保証金（受入保証金・必要保証金・保証金率）と、それに基づく新規建ての可否
- 建玉（ロング / ショート、平均建値）と返済時の損益確定
- 新規建て・決済の手数料、日割りの利息
- 追証・ロスカット・不足金

公開されている事実（計画書 §2）:

- **public の `GET /spot/pairs` に信用のパラメータがある。** 公式 docs（rest-api_JP.md「銘柄詳細」）によると、
  新規建て / 決済の maker / taker 手数料率、ロング / ショートの「利息率/日」、
  個人 / 法人の「リスク想定比率」とその適用終了日時、ロング / ショートの新規建て停止ステータスが返る。
  2026-07-25 と 2026-11-24 の生レスポンスで、信用対応の 5 ペア（btc / xrp / eth / sol / doge）だけが非 null だった。
  個人のリスク想定比率は `0.5`。CLI の `PairSchema` / `CachedPairSchema` はこれらを落としていた（Step 1 で修正済み）
- **保証金・追証・強制決済のルールは API docs には無く、bitbank の公表ルールにある**（計画書 §2.3。
  [信用取引ルール](https://bitbank.cc/guide/margin-trading-rule) と契約締結前交付書面の原文を 2026-11-24 に確認）。
  受入保証金合計額 = 差入保証金 + 建玉評価損益 − 未収費用、維持必要保証金額 = 建玉数量 × 平均建値 × リスク想定比率、
  保証金率 = 受入保証金合計額 ÷ 建玉（保有分）。追証は毎日 15 時の時点で維持必要保証金額が受入保証金合計額を上回ると発生し、
  解消期限は 24 時間。強制決済は随時「維持必要保証金額 × 0.5 > 受入保証金合計額」で発動し、新規発注中の注文を取り消して
  建玉すべてを成行で決済する。計算は口座単位。ただし「評価時の価格」が last / bid / ask のどれかは書かれていない。
  姉妹リポ bitbank-lab-mcp は API の値を表示するだけで、これらを計算するコードは持っていない（計画書 §2.5）
- **利息・手数料・`profit_loss` は、このリポの税務調査で実測済み**（`docs/dev/tax-roadmap.md`、
  `docs/dev/tax-evidence/ANSWERS.md` §4。計画書 §2.4）。利息は 0.04%/日を JST 0 時の時点の建玉に掛け、
  `interest = product × 0.0004 × またいだ 0 時の回数` が原精度で成立する。手数料は建て分を建玉に積み、
  決済時に建て分 + 決済分を一括精算する。`profit_loss` は値幅損益から手数料と利息を引いたネット値

判断が必要になった点:

1. **境界。** public のみを保つか。実口座の `margin-status` などを引いて本番の値に合わせるか
2. **コマンド形状。** 現物の `paper create-order` を拡張するか、本番と同じく別コマンドにするか
3. **public の API から取れないルール**（追証・強制決済の判定、利息の境界、評価価格）をどう扱うか
4. **ロスカット判定の粒度**と、観測できない区間（lazy tick の上限超え・足の取得失敗）の扱い
5. **[ADR-002](002-no-analysis-logic-in-cli.md)（CLI に分析ロジックを持たない）との関係**

## 決定

1. **paper に信用の新規建て・返済を足す。public のみの境界は変えない。** パラメータは
   `/spot/pairs` から引き、private / trade エンドポイントは叩かない。計算本体は `cli/paper-margin/` に置き、
   chaos `x09` の検査範囲をこのディレクトリまで広げる。
2. **コマンドは ADR-009 と同じ語彙にする。** `paper create-margin-order` を新設する。
   `--position-side` は必須、`--intent=open|close` は任意のクロスチェックとし、結果に
   `side × position_side` から導いた操作ラベルを載せる。現物の `paper create-order` は
   `--position-side` を `PARAM` で拒否する。状態は `paper margin-status` / `paper margin-positions` で見る。
   paper は実資金に触れないので `--execute` / `--confirm` は持たない。
   操作ラベルの純関数は Phase 7 と共有し、中立な `cli/margin-operation.ts` に置く。
3. **ライブで取れる値は毎回引き、公表ルールはそのとおりに再現し、どちらでも決まらない値は仮定として申告する。**
   - ライブ: 信用対応ペア、個人のリスク想定比率、信用の手数料率、利息率、新規建て停止（`/spot/pairs`）
   - 公表ルール（計画書 §2.3）: 受入保証金合計額・必要保証金額・保証金率の算式、新規建ての条件、
     追証（毎日 15 時に判定・期限 24 時間）、強制決済（随時・掛け目 0.5、全建玉を決済し新規発注中の注文を取消）、
     平均法、部分決済での手数料の按分
   - 実測済み（計画書 §2.4）: 利息の掛け方（決定 7）、手数料を建玉に積んで決済時に一括精算すること、
     返済の損益を手数料・利息控除後のネット値で確定すること
   - 仮定: 評価価格（v1 は ticker の last）、追証の解消判定（決定 4）、部分決済で積み上がった利息を按分すること。
   - 強制決済掛け目と追証の基準時・期限は公表ルールの値だが、API（public）からは取れない。仮定値と同じく
     `paper init`（または v3 → v4 の移行時）に state へ固定し、出典と確認日を付けて信用の全出力に
     `assumptions` として載せる。本番の値と一致する保証が無いことを出力と Skill で明示する
4. **判定は安全側に倒し、見えない区間は申告する。**
   - ロスカットは 1m 足の不利な極値（ロングは low、ショートは high）で口座全体の保証金率を評価する。
     割ったら全建玉をその極値で決済する
   - 同じペアの両建て（ロングとショートを同時に持つ）は、そのペアの建玉をまとめて安値と高値のそれぞれで評価し、
     評価損益が小さくなる方の 1 つの価格で判定・決済する。ロングを安値・ショートを高値で同時に評価することはしない。
     1 本の足の安値と高値は別の時刻に付いた価格で同時には成り立たず、重ねると実際には起こり得ない損失
     （同数の両建てなら足の値幅 × 数量）を毎回計上してしまうため。片建てでは上の書き方どおりになる
   - 建玉がある間は、未約定注文が無くても tick で足を取りに行く
   - lazy tick の 24h 上限を超えた区間は 4hour 足で判定し、`warnings` と `approximate` で申告する
   - 信用の走査は現物の `lastTickAt` とは別の走査済み時刻（`margin.lastScanAt`）で進める。足を取れなかった区間は
     走査済み時刻を進めず、次の tick で取り直す。現物の足の取得失敗とは独立させる（巻き込むと、走査済みの区間を
     もう一度走査して、後から建った建玉を前の足で評価してしまう）。走査済み時刻が now に届いていなければ、
     建玉・注文がまだ無い口座でも信用の注文を受け付けない
   - 追証は、本番の差入方法のうち paper で行える行為（建玉の返済・現物の売却）の直後に
     受入保証金合計額 ≥ 維持必要保証金額 となったときだけ解消する。価格の回復だけでは解消しない
     （本番の扱いは公表されていない）。現物の売却は JPY 建ての売り（JPY が増える）で、追証の基準時より後のものだけを
     数える（成行は売った直後に現在値で、指値と、その場で判定できなかった成行は、走査が約定した時刻の口座で判定する）。
     例外として、現物の足だけ取れずに信用の走査が先へ進んだ後で約定が確定した売りは、約定した時刻がもう走査済みなので、
     次に走査できた tick の窓の頭で判定する（判定が売りより遅れる近似）。例外は判定する時刻だけで、数える売りは変えない
     （約定時刻が追証の基準時より前の売りは、窓の頭が基準時より後でも数えない）。窓の中で約定した現物の JPY は、
     約定より前の時刻の評価には入れない（売りの代金で、売る前の強制決済をすり抜けないように）。
     期限までに解消しなければ期限の時刻で強制決済する
   - pairs から信用パラメータを読めなくなったペア（取扱終了・欄の欠落）は、最後に読めた値（`margin.lastParams`）で
     評価と返済を続け、`warnings` と `assumptions` で申告する。そのペアの新規建ては止める
5. **口座は現物と JPY 残高を共有し、v1 の保証金は JPY だけにする**（代用暗号資産は入れない）。
   個人口座を前提とする。ご利用可能額（審査で決まる与信枠）は再現しない。入金は持たないので、
   不足金が出たら新規建てを止める（返済は止めない。損の大きい建玉の返済で JPY が負になっても、含み益のある別の
   建玉が残ることがあり、それを返済できないと口座が固まる）。建玉が無くなった後の解消手段は `paper reset` だけになる。
6. **ADR-002 の例外は作らない。** 本 ADR の計算は取引所の約定・保証金・決済ルールの再現であり、
   相場の分析でも売買判断でもない。既存の paper（指値の約定判定・平均取得単価の損益）と同じ
   「シミュレーション」の範囲であり、CLAUDE.md の paper 例外節を広げるものとして扱う。
7. **利息と追証の判定は JST の暦で数える。** 利息は JST 0 時をまたぐたびに、その時点の建玉の `product × 日率` を積む
   （実測どおり）。追証は毎日 JST 15 時の時点で判定する（公表ルールどおり）。CLAUDE.md の「JST は表示用のみ」の例外になる。
   API のキー組み立てではなく取引所の暦の再現で、税務の年分判定と同じ扱いにし、境界の計算は `cli/date-utils.ts` の
   JST 関数に閉じる。

## 理由

### なぜ public のみを保つか（判断点 1）

paper の価値は「API キーなしで誰でも練習できる」ことにある（paper-trade Skill の compatibility は
「`.env` は不要」）。実口座の `margin-status` を引けば本番のしきい値に近づくが、信用審査済みのアカウントが
必要になり、練習の入口として成り立たない。実口座の値が仮想口座に混ざって「どこまでが仮想か」も
曖昧になる。本番に合わせ切れない部分は、仮定として申告することで補う（決定 3）。

### なぜ本番と同じ語彙か（判断点 2）

[`botter-runbook.md`](../botter-runbook.md) は「read-only → paper → dry-run → 本番」の順で進める。
paper で書いたコマンドが、名前空間の差し替え（`paper` → `trade`）だけで本番の dry-run に通る状態が、
練習の効果を最大にする。

- `paper create-order` に `--position-side` を足す案は、本番の `trade create-order` が
  `--position-side` を拒否する（ADR-009 決定 1）ので、練習した形が本番で通らない
- open / close の 2 コマンドに抽象化する案は、ADR-009 が案 C を捨てたのと同じ理由で捨てる
  （API の `side` と表示がずれたときの責任が CLI に来る）

### なぜ仮定値を state に固定して申告するか（判断点 3）

近似を黙って出すと、利用者（LLM を含む）は paper の保証金率を本番の目安として扱う。
間違いが静かな領域では、打ち切りや前提を申告するのがこのリポの線である
（[ADR-007](007-balance-history-reconstruction-in-cli.md) の 4 経路申告、
[ADR-006](006-reference-pnl-guard-scope.md) の表示ガード）。
state に固定するのは、CLI のバージョンアップで既定値が変わっても、既存の仮想口座の過去の結果が
こっそり変わらないようにするため。

### なぜ安全側に倒すか（判断点 4・決定 5）

paper と本番のずれの向きには非対称性がある。paper で生き残った戦略が本番でロスカットされるのが
最悪の失敗で、逆（paper のほうが厳しい）は練習としては無害である。よって、ずれは
「本番より早くロスカットされる」向きにだけ許す。

- 1m 足の極値で判定・約定させる
- 保証金を JPY だけにする（代用暗号資産を入れない分、保証金を少なく見積もる）
- 観測できない区間は粗い足で判定する

いずれもこの向きのずれである。現物の指値は 24h を超える区間を「警告して切り捨て」ているが、
信用でロスカットを見逃すと、本来ゼロになった口座が生き残り続ける。間違いの重さが違うので、
扱いも変える。

### なぜ ADR-002 の例外にしないか（判断点 5）

ADR-002 が CLI から締め出したのは、生データを渡せばモデルが再現できる「分析」（指標・スコアリング・判断）である。
ADR-004 / 007 / 008 はその例外として、モデルが再現できないか、再現の費用が用途を壊す計算を CLI に置いた。
本 ADR の計算は分析ではなく、取引所が口座に対して行う処理（約定・保証金・強制決済）の再現である。
既存の paper も同じ性質の計算を持つが、ADR-002 の例外リストには載っていない。
ここで例外として登録すると「分析を CLI に置いてよい条件」という例外の基準がぼやけるので、登録しない。
売買判断を出さない点も変わらない。

### なぜ追証の解消を行為に限るか（決定 4）

公表ルールが挙げる追証の差入方法は、入金・暗号資産の預入・現物の売却・建玉の決済の 4 つで、価格の回復は無い。
書面も「追加保証金が預託されなかった場合」に強制決済するとしており、価格の回復だけで解消扱いになるかは読み取れない。
価格の回復でも解消できる扱いにすると、本番では強制決済される口座が paper では生き残り得る。安全側の原則（判断点 4）に従い、
paper で行える 2 つの行為の直後に条件を満たしたときだけ解消とする。

### なぜ利息と追証の判定を JST にするか（決定 7）

「JST は表示用のみ」は、API のキー（ローソク足の `YYYYMMDD` など）を UTC で組み立てるための規約である。
利息の境界と追証の基準時は API のキーではなく、取引所が口座を処理する暦で、利息は実測で JST 0 時、
追証は公表ルールで毎日 15 時と分かっている。UTC に寄せると、paper の処理が本番と 9 時間ずれた時刻に起きる。税務の年分判定（JST の 1/1〜12/31）と
同じ種類の例外であり、同じく `cli/date-utils.ts` に閉じてホスト TZ に依存させない。

## 検討した代替案

| 案 | 判定 |
|---|---|
| 実口座の `margin-status` / `margin-positions` から本番のしきい値を引く | 却下。API キーと信用審査が要り、paper の入口が成り立たない。`x09` も崩れる |
| `paper create-order` に `--position-side` を足す | 却下。本番では拒否される形を練習することになる |
| 追証・強制決済を実装しない（建玉と損益だけ持つ） | 却下。レバレッジの練習で最も学ぶべき「強制決済で建玉が消える」体験が抜け、paper で生き残った戦略を本番に持ち込む危険がかえって増える |
| 仮定値をコード定数だけで持ち、state に書かない | 却下。バージョンアップで既存の仮想口座の結果が黙って変わる |
| 24h を超える区間を現物と同じく切り捨てる | 却下。ロスカットの見逃しは「静かな誤り」で、現物の指値の未約定とは重さが違う |
| 利息の境界・追証の基準時を UTC で数える（「JST は表示用のみ」に合わせる） | 却下。本番と 9 時間ずれる。境界は取引所の暦であって API のキーではない |
| 追証は価格の回復でも解消する | 却下。公表ルールの差入方法に無く、本番より強制決済が遅れる向きのずれになる |
| 代用暗号資産を v1 から入れる | 見送り。掛目（0.5）は公表ルールにあるが、時価評価の価格（#PM-4）がまた仮定になる。保証金を少なく見積もる現行案は安全側なので、需要を見て足す |

## 影響

- **追加:** `cli/paper-margin/`（パラメータ・保証金・建玉・利息・ロスカット）、
  `cli/commands/paper/create-margin-order.ts` / `margin-status.ts` / `margin-positions.ts`、
  `cli/margin-operation.ts`（Phase 7 と共有）
- **変更:** `cli/commands/public/pairs.ts` と `cli/pairs-cache.ts` が `margin_*` / `stop_margin_*` を通すようになる
  （`bitbank pairs` の出力が増え、pairs キャッシュは version 2）。`cli/paper-fill.ts` は建玉があるときにも tick する。
  `paper create-order` は `--position-side` を拒否する。`paper pnl` の `perPair` / `total` は現物のみのままで、
  `margin` 節が増える
- **state は v4 になる。** v3 以前からは自動で移行するが、**v4 を書いた後に古い CLI に戻すと読めない**（ダウングレード不可）
- **chaos:** `x09` の検査範囲に `cli/paper-margin/` を足す（足さないと新しいコードに検査が効かない）。
